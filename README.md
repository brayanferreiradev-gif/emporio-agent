# Empório da Música — Customer Support Agent

> 🇺🇸 English · 🇧🇷 [Português](README.pt-BR.md)

A text-chat agent for **Empório da Música**, a (fictional) musical-instrument store in Campo Grande/MS.
It answers customers as "Dó", a friendly store assistant, and decides on its own **when to look up live data**
(prices, promotions, stock, orders) and **when to consult the policy manual** (returns, payments, shipping, warranty).

Built for the Artefact *AI Engineer* technical case. Python, Gemini API (free tier), no framework beyond the official SDK.

```
Cliente: Quanto custa o Takamine GD20? Dá pra parcelar?
Dó:      O Takamine GD20 Dreadnought Natural custa R$ 2.199,00 (R$ 2.089,05 no PIX).
         No cartão, até 12x de R$ 183,25 sem juros. Quer calcular o frete pra sua cidade? 🎸
```

* **Example conversations:** [`examples/`](examples) (5 scripted scenarios, generated by running the real agent — see below)
* **Tests:** 39 deterministic tests, no API key needed (`pytest`)

## 1. Quick start

Requirements: Python 3.10+ and a free Gemini API key ([get one here](https://aistudio.google.com/apikey), no credit card).

```bash
git clone https://github.com/brayanferreiradev-gif/emporio-agent.git && cd emporio-agent
python -m venv .venv
# Windows: .venv\Scripts\activate      macOS/Linux: source .venv/bin/activate
pip install -r requirements.txt

cp .env.example .env          # then edit .env and paste your key into GEMINI_API_KEY
python -m emporio             # start chatting
```

Useful options:

| Command | What it does |
|---|---|
| `python -m emporio --verbose` | also prints every tool call the agent makes (great to see the reasoning) |
| `python -m emporio --session maria` | named conversation; history is saved to `var/sessions/maria.json` and resumed next time |
| `python -m emporio --new` | start the session from scratch (or type `/nova` in the chat) |
| `python -m emporio --now 2026-03-05T15:00` | simulate the current date/time (see "Clock" below) |
| `pytest` | run the tests (offline, < 1 s) |
| `python scripts/run_examples.py` | regenerate the example conversations (live API calls) |

Things worth trying: *"Quais violões de aço até R$ 800?"*, *"Cadê meu pedido 8?"* (the agent asks for e-mail/phone —
try `anacarol.ferreira@coldmail.com`), *"Me arrependi, posso devolver o pedido 7?"*, *"Vocês vendem palheta?"*.

> **Clock.** The CSVs are a frozen snapshot (latest order: 2026-03-22) but the real date is later, so every order
> would look months old. `--now` / `EMPORIO_NOW` simulates a date; without it the real clock is used. The examples use it.

## 2. How it works

```
 customer message
        │
        ▼
 ┌──────────────────────────────  Agent (emporio/agent.py)  ─────────────────────────────┐
 │  system prompt (persona + rules)  +  last 24 messages  +  new message                  │
 │        │                                                                               │
 │        ▼              tool call(s)                                                     │
 │     Gemini  ───────────────────────────►  Tools (emporio/tools.py)                     │
 │        ▲                                   │  search_products · list_promotions        │
 │        └────────── tool results ◄──────────┤  get_payment_options · get_shipping_info  │
 │   (loop, max 6 round trips)                │  get_store_info · search_policies         │
 │                                            │  get_order_status · check_return_elig...  │
 │                                            └─ get_product_details · escalate_to_human  │
 └────────────────────────────────────────────────────────────────────────────────────────┘
        │                                         │                       │
        ▼                                         ▼                       ▼
   final reply                    data/*.csv (cleaned in memory)   data/store_policies.md
   saved to var/sessions/                  + business rules          (BM25 section search)
```

| File | Role |
|---|---|
| `emporio/agent.py` | Function-calling loop, model fallback, retries, conversation memory notes |
| `emporio/prompts.py` | Persona, grounding rules, tool-routing guide (dynamic: date + catalogue overview) |
| `emporio/tools.py` | The 10 tools the model can call; identity checks; hand-off tickets |
| `emporio/rules.py` | Business rules as plain code: pricing/PIX, instalments, shipping, opening hours, return windows |
| `emporio/catalog.py` | Accent/plural-insensitive product search with field weights |
| `emporio/policies.py` | BM25 retrieval over the policy manual + synonym table |
| `emporio/data.py` | CSV loading, cleaning, data-quality report |
| `emporio/session.py` | Persistent history + verification state per conversation |
| `scripts/ingest_policies.py` | PDF → Markdown conversion of the manual (PyMuPDF, tables included) |
| `scripts/run_examples.py` | Runs scripted conversations against the real agent → `examples/` |

## 3. Technical decisions and why

### Approach: function calling with deterministic tools (hybrid)
The case asks the agent to know *when* to query data and *when* to consult policy. Function calling maps to that
directly: each tool is one data source or one business rule, and the model picks the tool(s) from the question.
I rejected the alternatives on purpose:

* **Pure RAG** over everything: prices, stock and orders are structured and must be exact. Retrieval over text chunks of a
  CSV is lossy and invites invented numbers.
* **Text-to-SQL agent**: flexible, but fragile (wrong joins, forgotten `is_active` filter, leaking other customers' orders) and
  unsafe for private order data. A fixed set of parameterised tools gives the same coverage here with far less risk.
* **ReAct-style free text loop**: native tool calling gives validated arguments and parallel calls without parsing.

**Rules live in code, not in the prompt.** Promotion pricing, the "PIX discount never stacks on promotions" rule, instalment
minimums, the free-shipping threshold, opening hours and the 7/30-day return windows are plain functions in `rules.py`.
The tools hand back **pre-formatted** values (`"R$ 5.519,08"`), so the model never does arithmetic or date math. That removes the
most common class of LLM mistakes and makes the behaviour unit-testable (39 tests).

### Model and provider: Gemini API, free tier
I first considered a local 7B model via Ollama (free, private). On the target machine (6 GB laptop GPU) a 7B model would
be slow and noticeably less reliable at tool calling in Portuguese, and reliability matters more than privacy here
because the data is fictional. Gemini has a free tier with strong native function calling and Portuguese.

Practical findings while building (free tiers move fast, so the code is defensive):

* `gemini-2.5-flash` returns **404 "no longer available to new users"**, so it cannot be the default.
* The newest models return **503 "high demand"** in bursts. `emporio/config.py` defines a **fallback chain**
  (`gemini-3.6-flash → gemini-3.5-flash → gemini-3.1-flash-lite`, overridable with `GEMINI_MODEL` / `GEMINI_FALLBACK_MODELS`);
  the first healthy model answers. SDK-internal retries are capped to one attempt because waiting on an overloaded model
  took 20 s+ while falling back takes ~1 s.
* **`thinking_level="low"`**: same answers, ~4× faster in my measurements (≈7 s vs ≈30 s for a catalogue question
  with one tool call). Configurable with `GEMINI_THINKING`.

### Retrieval architecture
* **Policies**: the manual has ~10 sections, so a transparent **BM25 keyword search over section-level chunks** with a small
  Portuguese synonym table (e.g. *devolver → devolução/arrependimento*) is enough. No vector DB, no embedding calls, easy to debug.
  The PDF is converted once to Markdown by `scripts/ingest_policies.py` (PyMuPDF, tables preserved); the runtime only reads the `.md`.
* **Catalogue**: lexical search with accent/plural normalisation and field weights (name/brand > category > description/specs).
  Model numbers match however typed (`GD20`, `gd-20`, `gd 20`). With ~65 items and part numbers, exact-ish matching beats embeddings.
  Out-of-stock, discontinued and "coming soon" products are returned in a separate `matches_not_for_sale` list with alternatives
  (manual §7.3: never confirm availability without checking, offer alternatives).

### Prompt strategy
The system prompt (`prompts.py`) has: persona and tone (from manual §7.1: *informal but professional, like a friend who knows music*),
a **golden rule** (anything about prices/stock/orders/policies must come from a tool result in this conversation, otherwise say
"I don't know" and offer a human), a **tool-routing table** (which question → which tool), and **numbered rules** (promotion display,
availability, scope, privacy, returns, complaints, prompt-injection resistance). It is dynamic: it injects the current date/time and an
overview of which categories actually have products, so the model doesn't promise instruments the store doesn't list.
Replies follow WhatsApp conventions (short, `*bold*`, at most one emoji).

### Privacy and safety
* Order data requires **order number + matching e-mail or phone** (LGPD, manual §9). A failed check returns the same generic message
  whether the order or the contact was wrong (no information leak), and after 3 failures the chat is locked and the agent offers a human.
  The identity check lives in the tool, **not** in the prompt, so a prompt injection cannot bypass it.
* The model cannot execute returns, refunds or cancellations; it can only open a **hand-off ticket** (`var/handoffs.jsonl`).
* Scope: accessories are politely redirected, unrelated topics declined, and the manual is treated as an internal document (paraphrased, not quoted).
* Tool output and customer text are declared as *data, not instructions* in the prompt.

### Interface and persistence
* **CLI** (the case says the focus is the agent working). A tiny interface keeps the review about the agent logic.
* **Persistence**: one JSON file per session (`var/sessions/<id>.json`) with history and verification state, resumed automatically.
  The model sees the last 24 messages plus short *internal notes* of what tools returned (e.g. product ids), so follow-ups like
  "tell me more about the cheapest one" don't trigger new searches. Notes are never shown to the customer.

### Data handling
`emporio/data.py` parses and cleans the CSVs; `quality_report()` lists what was found (all covered by tests):

| Finding | Handling |
|---|---|
| Product 96 is `active` with stock 0 | availability = `out_of_stock` |
| Product 130 is `coming_soon` with stock 2; product 136 is `discontinued` with stock 13 | never sellable; alternatives suggested |
| Categories 6, 7, 8 (woodwinds, brass, orchestral strings) have **no products**, though the manual says the store sells them | the agent states the catalogue has none now (system data wins over the manual) |
| 21 of 25 promotions have `is_active = 0` (only 4 are running) | only active promotions count; expired ones are never offered |
| Orders 3 and 20: recorded total ≠ sum of items at current prices | recorded total is used as-is |
| E-mail `bruno.martins@jmail.com` belongs to two customers (11 and 43) | verification requires **order + contact** to belong together, never contact alone |
| Orders dated after the simulated "now" | treated as non-existent |

## 4. Assumptions (ambiguities and contradictions in the material)

1. **Phone/WhatsApp.** The manual gives `(67) 3341-4444` (cover and company data) and `(67) 3321-4500` (WhatsApp section). I use **3341-4444** everywhere
   (`policies.CANONICAL_FIXES`) so the agent never gives two answers. Likewise the e-mail is written without the accent (`contato@emporiodamusica.com.br`).
2. **Instalments.** The summary table says "minimum R$ 100/instalment"; §3.1 is more specific (up to 3x from R$ 50, 4–6x from R$ 80, 7–12x from R$ 100). I implemented **§3.1**.
3. **Delivery region.** "Metropolitan region of Campo Grande" isn't defined; only **Campo Grande** is treated as local (flat R$ 35 under R$ 500, free from R$ 500).
   Other cities get the Correios/Jadlog table and a note that the exact price depends on the ZIP code (not computable here).
4. **Returns.** There is no channel column, so all orders are treated as **online** (§4.1 regret right applies). There is no delivery timestamp, so for
   delivered orders `estimated_delivery` stands in for the receipt date. The 30-day defect-swap window is counted **from purchase**, as §4.2 literally says;
   the 90-day legal warranty from receipt is reported when relevant.
5. **Unshipped orders.** The manual has no cancellation policy, so the agent says so and hands off instead of improvising.
6. **Holidays.** Only fixed-date national holidays are considered when answering "are you open?"; movable ones (Carnival, Good Friday) aren't tracked.
7. **Partner stores.** The manual says to suggest partner stores "when possible", but no list exists; the agent recommends "stores specialised in accessories" without inventing names.
8. **Hand-off.** There is no ticketing system, so tickets are appended to a local file (`var/handoffs.jsonl`) as a stand-in.

## 6. Known limitations and what I'd do with more time

* **Latency and availability** depend on the free Gemini tier: replies take ~3–15 s and the fallback chain can switch models between turns
  (answers stay consistent because rules are in code, but tone may vary slightly).
* **LLM evaluation is partial.** `evals/battery.py` runs 134 live scenarios (catalogue, payments, shipping, hours, policies, order lookups, returns, out-of-scope, prompt injection, other languages) with automatic checks: expected tool called, forbidden phrases absent, and *every R$ amount in a reply must come from a tool result*. First full run (118 scenarios): 104 passed, and the failures drove real fixes (promotion listing, price sorting, invented reasons, leaked notes, language). After the fixes the free **daily quota ran out**, so the full re-run could not be completed; affected scenarios were re-run individually on other Gemini models. Next step: a full green run in CI and an LLM-as-judge for tone.
* **Retrieval is lexical.** Fine for 65 products and 10 manual sections; I'd add embeddings (hybrid search) when the catalogue reaches the 300+ items the manual mentions.
* **Shipping outside Campo Grande** can't be priced; I'd integrate the Correios/Jadlog quote APIs by ZIP code.
* **Hand-off is a file.** A real version would create a ticket in the helpdesk/CRM and notify staff, and would collect contact consent explicitly.
* **Single-channel, single-user CLI.** The same `Agent` class could sit behind a FastAPI/WhatsApp webhook; sessions would move from JSON files to a database.
* **Streaming and observability.** Stream replies to cut perceived latency; log traces (tool calls, tokens, latency) to a tracing backend.
* **Holidays and store calendar** should come from a calendar source instead of a fixed list.
* **Price/stock freshness**: data is loaded once at start-up; a real deployment reads from the live system on each call.

## 7. Use of AI coding assistants

I built this with **Claude Code** (Anthropic's CLI/desktop coding agent, model *Claude Sonnet 5.5*) as a pair-programmer, working in short iterations.
How the work was split:

* **My decisions:** the deliverable's scope, the choice of an API model over a local 7B (hardware and reliability), Gemini as provider, the project location, and reviewing each step.
* **Claude Code:** read the brief, the manual (PDF) and the CSVs; proposed the architecture; wrote the code, tests and this README;
  ran the code against the live API and iterated on what it observed.
* **Things found by running, not by guessing:** `gemini-2.5-flash` is retired for new keys (404); the newer models are intermittently overloaded (→ fallback chain);
  `thinking_level="low"` cut latency ~4×; the first model answers used `**bold**` (→ prompt now asks for WhatsApp formatting); the agent forgot product ids between
  turns and re-searched (→ internal notes in the history); a test that I (the assistant) wrote with a wrong expectation (599 ÷ 6 ≥ R$ 80 → 6 instalments, not 5) was caught by the test run.
* **Verification:** every business rule has a unit test; the example transcripts come from the real agent, unedited.

The commit history shows the actual progression (scaffold → data/ingestion → rules/tools/agent → resilience → tests → examples → docs).
